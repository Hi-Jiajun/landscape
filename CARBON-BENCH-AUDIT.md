## 2. Source-Code & Kernel Verification of Upstream Engineering Findings

### 2.1 Finding 1: `pppoe_pnet_filter` + `ETH_P_ALL` Running on 100% of TX and RX PPPoE Data Frames

- **Source Files Verified (`feat/flow-l4-port-rules @ 84472315`)**:
  1. `landscape-ebpf/src/bpf/pppoe_client.bpf.c:16-49`: `SEC("socket") int pppoe_pnet_filter(struct __sk_buff *skb)` performs up to **three `bpf_skb_load_bytes()` calls** (`offset 12` EtherType, `offset 14` 6-byte PPPoE base header, `offset 20` 2-byte PPP protocol) and returns `0` for `ETH_P_PPP_IPV4` / `ETH_P_PPP_IPV6`.
  2. `landscape-ebpf/src/pppoe/mod.rs:20-56`: `open_raw_socket()` creates `socket(AF_PACKET, SOCK_RAW | ..., htons(ETH_P_ALL))` (`0x0003`) and `bind_raw_socket()` binds `sll_protocol = 0x0003_u16.to_be()` (`ETH_P_ALL`) to the WAN interface (`enp2s0.4091`).
  3. `landscape/src/wan_service/pppoe_client/runtime.rs:49`: `landscape_ebpf::pppoe::start(config.index)` keeps this `AF_PACKET` socket open for the entire lifetime of the PPPoE session (to exchange `LCP Echo` frames and watch for `PADT`).
- **Exact Packet-Count Proof from [04-m2b-pppoe-3way.log](logs/04-m2b-pppoe-3way.log) (lines 87-90)**:
  - `tc_wan_egress_route` runs (6s): `7,168,152`
  - `tc_wan_ingress_intro` runs (6s): `305,470`
  - **Exact Sum (`TX + RX`)**: **`7,473,622`** vs `pppoe_pnet_filter` runs: **`7,472,873`** (`99.99%` match).
- **Why the True Savings Exceed `38.41 ns/pkt`**:
  - Because `sll_protocol == htons(ETH_P_ALL)` registers the socket on `dev->ptype_all` in Linux `net/core/dev.c`, **every outgoing packet** enters `dev_queue_xmit_nit()`, executing `skb_clone()` -> `packet_rcv()` -> `pppoe_pnet_filter` (`38.41 ns`) -> `consume_skb()`, and **every incoming packet** enters `ptype_all` `deliver_skb()` before TC ingress.
  - **Soundness of Proposed Optimization (Verified)**:
    - *Option A (Minimal 5-line fix — zero TX cost)*: Split or rebind `sll_protocol` away from `ETH_P_ALL` (`0x0003`) to `ETH_P_PPP_SES (0x8864)` + `ETH_P_PPP_DISC (0x8863)`. In Linux `net/core/dev.c`, protocol-specific packet sockets live in `ptype_base`, which is **never** walked on egress (`dev_queue_xmit_nit` only walks `ptype_all`), immediately eliminating **100% of TX clones and filter runs (`95.9%` of the 7.47M calls)**.
    - *Option B (Zero-datapath-overhead architecture — zero TX and zero RX cost)*: `tc_intro_pppoe()` in `landscape-ebpf/src/bpf/tc_wan_ingress_intro.bpf.c:44-46` **already** parses `ppp->protocol` on every incoming `ETH_P_PPP_SES` frame and branches on `if (protocol != ETH_P_PPP_IPV4 && protocol != ETH_P_PPP_IPV6)`. Emitting those rare control frames (`LCP`/`IPCP`/`IPV6CP`/`PAP`/`CHAP` + `ETH_P_PPP_DISC` `PADT`, `<1 pps` in steady state) to userspace via `bpf_ringbuf_output()` while binding the userspace TX raw socket with `sll_protocol = 0` (which Linux `af_packet.c` treats as TX-only with **zero** `ptype` hook registration) removes `AF_PACKET` from **100% of both TX and RX data packets**, reclaiming both `38.41 ns/pkt` of BPF execution and `skb_clone`/`consume_skb` overhead (~15-20% total PPPoE CPU).

### 2.2 Finding 2: Short-Lived HTTP `CPS` Ceiling (`~1.1k - 1.7k CPS @ 3% CPU`) & EIM NAT44 Interaction

- **Source Files Verified (`feat/flow-l4-port-rules @ 84472315`)**:
  1. `landscape-common/src/wan_service/nat/config.rs:43` & `landscape-ebpf/src/stages/nat4.rs:58,78-84`: `NatConfig::default()` seeds `32768..=65535` = **`32,768` external TCP ports** into `napt_tcp_ports` (`BPF_MAP_TYPE_QUEUE`).
  2. `landscape-ebpf/src/bpf/nat_v4/tc_nat4_packet.h:45-61`: EIM port allocation keys `napt_from_lan` by `(internal_addr, internal_port, proto) -> external_port`. Across `16` LAN source IPs (`16 x 28,232 = 451,712` ephemeral client 2-tuples), every new `(src_ip, sport)` pops 1 port from the `32,768`-port queue (`tc_nat4_packet.h:54`; `TC_ACT_SHOT` when empty).
  3. `landscape-ebpf/src/bpf/nat_v4/nat4_ct_timer.h:16, 18, 204-208, 253`: Each new CT starts a `1s` report timer (`NAPT_CT_REPORT_INTERVAL_NS`). Even when HTTP `GET` + `FIN/FIN` completes in `0.2 ms`, `status` only enters `NAPT_CT_WAIT_TCP_CLOSE` on the next `1s` timer tick (`lines 204-208`), which then arms `NAPT_TCP_CLOSE_TIMEOUT_NS = 6s` (`line 18`). Total WAN port hold time is therefore **`~7.0 seconds`** (`32,768 / 7.0s = 4,681 ports/s` hard ceiling before SYN RTO). Once `napt_tcp_ports` drains in `<0.5s`, dropped SYNs trigger Linux `1.0s` initial SYN RTO backoff across the `128` client sockets — explaining why **Run 1 always achieves `1,613 - 1,690 CPS`** (starting with a full `32,768`-port queue) while **Runs 2-3 settle at `1,099 - 1,446 CPS`** at `97%` DUT CPU idle!
  4. `landscape-ebpf/src/bpf/nat_v4/nat4_ct_timer.h:297-298` & `51-54` *(Refining [README.md](README.md)'s initial line citation)*:
     - `napt_ct_status_can_activate()` (`lines 51-54`) only prevents transitioning `status` back to `NAPT_CT_ACTIVE` (returning `TC_ACT_OK` at line 305).
     - The **actual `TC_ACT_SHOT` drop** on a reused 4-tuple `SYN` is **lines `297-298`**:
       ```c
       if (status == NAPT_CT_WAIT_TCP_CLOSE)
           return napt_tcp_phase_is_syn(tcp_phase) ? TC_ACT_SHOT : TC_ACT_OK;
       ```
  5. `landscape-ebpf/src/bpf/nat_v4/tc_nat4_packet.h:85, 153` & `tc_nat4.h:73-79` *(Interaction with Full-Cone EIM vs Restricted `allow_reuse=0`)*:
     - `napt_dynamic_remote_allowed()` is currently invoked on **both** outbound `napt_lan_state` (`line 85`) and inbound `napt_wan_state` (`line 153`). When `allow_reuse == 0`, if a LAN socket reuses `(internal_addr, internal_port)` to connect to a *different* destination `(dst_addr, dst_port)` (`:8080` vs `:8081`), outbound `napt_lan_state` drops the `SYN`!
     - **Clean RFC 4787 / RFC 6191 Remediation**:
       1. **Same-4-tuple `SYN` Reopen (`nat4_ct_timer.h:297-298`)**: On outbound `NAPT_GRESS_LAN` TCP `SYN` when `status == NAPT_CT_WAIT_TCP_CLOSE`, atomically reset `tcp_flags` and CAS `status -> NAPT_CT_ACTIVE` (RFC 6191 / RFC 5382 `TIME_WAIT` reopen), keeping `mapping->state_ref` intact.
       2. **Immediate Close-Timer Arming & Wider Port Pool**: Arm `NAPT_TCP_CLOSE_TIMEOUT_NS` (or a shorter `TIME_WAIT` fast-recycle threshold when queue pressure is high) immediately when `napt_tcp_track_flags` observes `NAPT_TCP_BOTH_FIN` / `RST` rather than waiting for the `1s` `NAPT_CT_REPORT_INTERVAL_NS` tick, and optionally widen default `tcp_range` from `32768..65535` (`32k`) to `1024..65535` (`64k`).
       3. **True RFC 4787 EIM + APDF Outbound Port Sharing (`tc_nat4_packet.h:85, 153, 165`)**: Allow outbound LAN->WAN CTs to share an active `(internal_addr, internal_port) -> external_port` dynamic mapping across distinct `(dst_addr, dst_port)` targets (`mapping->state_ref` already reference-counts multiple CTs!), and check `mapping->allow_reuse` **only** when `!ct` on WAN ingress (`tc_nat4_packet.h:164`). That preserves 100% drop of unsolicited WAN traffic under `allow_reuse=0` (Port-Restricted Cone, EIM + APDF) while keeping `allow_reuse=1` as Full-Cone (EIM + EIF), multiplying effective port capacity by `N_destinations`.
